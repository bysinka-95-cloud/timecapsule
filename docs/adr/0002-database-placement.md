# ADR-0002. Размещение базы данных

- Статус: принято
- Дата: 2026-10-16

## Контекст

В ЛР2 приложение TimeCapsule и PostgreSQL работали на одном экземпляре EC2 в default VPC.
В ЛР3 приложение переносится в собственную сеть `timecapsule-dev-vpc` (`10.6.0.0/16`)
с публичными и приватными подсетями в зонах `eu-central-1a` и `eu-central-1b`.
Нужно решить, где разместить базу данных. Требования: база не должна быть доступна
из интернета, приложение должно находить базу по постоянному имени, расходы должны быть
минимальными (учебный аккаунт, бюджет около $31 за 3 месяца).

## Решение

Размещаем PostgreSQL на отдельном экземпляре `timecapsule-dev-db` в приватной подсети
`timecapsule-dev-private-a` без публичного адреса. Таблица `private-rt` содержит только
локальный маршрут. Security Group `timecapsule-dev-db-sg` пропускает порт 5432 только
от `timecapsule-dev-web-sg`, а SSH только от `timecapsule-dev-bastion-sg`. Файл `pg_hba.conf`
пускает только пользователя `timecapsule` в базу `timecapsule` из `10.6.0.0/24`.
Приложение обращается к базе по имени `db.timecapsule.internal` из приватной зоны Route 53.

## Рассмотренные альтернативы

- На одном сервере с приложением, как в ЛР2. Самый простой и дешёвый вариант: один
  экземпляр, база слушает только `localhost`. Отказались, потому что приложение и база
  делят ресурсы и диск. Взлом приложения сразу даёт доступ к файлам базы. Базу нельзя
  обновлять, масштабировать или пересоздавать отдельно от приложения.
- На отдельном сервере в публичной подсети. Пакеты и обновления ставятся напрямую
  через Internet Gateway, NAT Gateway не нужен. Отказались, потому что у сервера есть
  публичный адрес и маршрут в интернет. Защиту обеспечивают только Security Group и
  `pg_hba.conf`: одна ошибка в правиле открывает базу всему интернету.
- На отдельном сервере в приватной подсети (выбрано). У сервера нет публичного адреса
  и маршрута в интернет, поэтому из интернета к нему нельзя обратиться даже при ошибке
  в Security Group. Минус: для обновлений нужен временный NAT Gateway.
- Управляемая база Amazon RDS. AWS сам выполняет обновления, резервное копирование и
  восстановление. Отказались, потому что эту тему ещё не изучали в курсе.

## Последствия

- Плюс: три независимых уровня защиты: нет публичного адреса и маршрута, `db-sg`, `pg_hba.conf`.
- Плюс: базу можно остановить, обновить или пересоздать отдельно от приложения.
  При смене адреса нужно изменить только запись `db` в зоне `timecapsule.internal`, `.env` не меняется.
- Минус: у базы нет постоянного выхода в интернет. Обновления устанавливаются так:
  `scripts/nat-up.sh` создаёт временный NAT Gateway и маршрут `0.0.0.0/0` в `private-rt`,
  на `db-server` выполняется `sudo dnf -y update`, затем `scripts/nat-down.sh` удаляет маршрут,
  шлюз и освобождает Elastic IP. NAT Gateway стоит около $0,052 в час плюс $0,052 за ГБ трафика,
  поэтому одно обновление стоит несколько центов. Постоянный NAT Gateway стоил бы около $1,25 в сутки,
  то есть больше всех остальных ресурсов вместе.
- Минус: два экземпляра вместо одного, плюс приватная зона Route 53 ($0,50 в месяц).
  Администрирование сложнее: SSH только через bastion.
- `app-server` использует Elastic IP `timecapsule-dev-app-eip`, чтобы адрес приложения
  (`APP_URL`, адрес в браузере) не менялся после остановки и запуска сервера. Elastic IP стоит
  $0,005 в час всегда, даже когда сервер остановлен. Когда перед приложением появится балансировщик
  нагрузки, пользователи будут обращаться к DNS-имени балансировщика. Тогда `app-server` можно будет
  перенести в приватную подсеть, а Elastic IP освободить.
- Риск: база работает на одном экземпляре в одной зоне `eu-central-1a`. При отказе зоны или
  диска приложение потеряет базу. Резервных копий пока нет.
