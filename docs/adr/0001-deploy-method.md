# ADR-0001. Способ доставки кода на сервер

- Статус: принято
- Дата: 2026-10-12

## Контекст

TimeCapsule работает на одном экземпляре EC2 (Amazon Linux 2023, nginx, PHP-FPM, PostgreSQL).
Код приложения хранится в публичном репозитории GitHub `bysinka-95-cloud/timecapsule`.
Новую версию нужно выпускать быстро и одинаково каждый раз.
Каждый выпуск состоит из четырёх шагов: получить код, установить библиотеки,
создать недостающие таблицы, перезапустить PHP-FPM.
Ограничения: один сервер, нет системы CI/CD, доступ к серверу только по SSH с ключом.

## Решение

Используем скрипт `~/deploy.sh` на сервере. Скрипт выполняет `git pull --ff-only`,
`composer install`, `php bin/init-db.php` и `systemctl reload php-fpm`.
Скрипт останавливается при первой ошибке (`set -euo pipefail`) и в конце печатает
текущий коммит. Разработчик запускает скрипт со своего компьютера одной командой:

```bash
ssh -i ~/.ssh/bysinka_95-keypair.pem ec2-user@<Public-IP> ./deploy.sh
```

Единственный источник кода — репозиторий. Сервер сам забирает код из GitHub по HTTPS.

## Рассмотренные альтернативы

- Копирование файлов через `scp` с компьютера разработчика. Нет связи с репозиторием:
  нельзя узнать, какая версия работает на сервере. Легко пропустить файл.
  Откат выполнить трудно. Шаги `composer install` и `init-db` нужно выполнять отдельно.
- `git pull` и остальные команды вручную на сервере по SSH (вариант A). Версия
  известна по коммиту, откат выполняется через `git revert`. Но каждый раз нужно
  вручную набирать четыре команды. Можно пропустить шаг или выполнить шаги не по порядку.
- Система CI/CD (например, GitHub Actions). Деплой запускается автоматически после `git push`.
  Отказались, потому что эту тему ещё не изучали в курсе. Ещё нужно хранить ключ SSH
  в секретах GitHub.

## Последствия

- Плюс: деплой выполняется одной командой, шаги всегда одинаковые и идут в одном порядке.
- Плюс: на сервере работает известный коммит, откат выполняется через `git revert` и повторный деплой.
- Плюс: `git pull --ff-only` не смешивает ручные правки на сервере с новым кодом.
- Минус: скрипт хранится только на сервере и не входит в репозиторий. При замене сервера его нужно создавать заново.
- Минус: во время `git pull` и `composer install` сайт несколько секунд работает со смесью старых и новых файлов.
- Минус: деплой запускает человек. Нет автоматических тестов перед выпуском,
  поэтому ошибка попадает на сервер (проверено в задании 13).
- Риск: сервер один. Если экземпляр EC2 недоступен, сайт тоже недоступен.
