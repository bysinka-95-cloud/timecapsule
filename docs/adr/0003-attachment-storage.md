# ADR-0003. Хранение вложений пользователей

- Статус: принято
- Дата: 2026-10-27

## Контекст

В ЛР2 и ЛР3 вложения капсул (картинки и PDF) хранились в папке `storage/uploads`
на корневом томе EBS сервера `timecapsule-dev-app`. Такой сервер нельзя заменить новым
или запустить рядом второй: файлы пользователей есть только на его диске, и при удалении
экземпляра они пропадут. Нужно выбрать хранилище, которое не зависит от сервера приложения.
Ограничения: учебный аккаунт с минимальным бюджетом, файлы до 5 МБ, к файлам капсулы
имеет доступ только тот, кому приложение разрешило.

## Решение

Храним вложения в бакете Amazon S3 `timecapsule-dev-uploads-bysinka-95` под префиксом `uploads/`.
Бакет закрыт для публичного доступа, шифруется SSE-S3, политика бакета запрещает запросы без HTTPS.
Приложение работает с бакетом от имени роли `timecapsule-dev-app-role` через SDK, ключей доступа
на сервере нет. Политика роли `timecapsule-dev-app-s3` разрешает только `s3:GetObject`,
`s3:PutObject` и `s3:DeleteObject` для `uploads/*`. Файл пользователь получает по подписанному URL
сроком 5 минут: приложение проверяет права на капсулу и перенаправляет браузер (302) в S3.

## Рассмотренные альтернативы

- Диск EBS сервера приложения, как в ЛР2 и ЛР3. Самый простой вариант, без новых сервисов.
  Отказались, потому что том привязан к одному экземпляру в одной зоне доступности.
  Два сервера не могут работать с одними файлами, при удалении экземпляра файлы удаляются вместе
  с корневым томом. Файлы проходят через PHP и nginx, это нагружает сервер.
- Общая файловая система Amazon EFS. Несколько серверов в разных зонах монтируют одну папку,
  код приложения почти не меняется. Отказались, потому что EFS стоит дороже S3 за ГБ, требует
  точек монтирования в подсетях и правил Security Group для NFS. Файлы всё равно отдаёт
  сервер приложения. Версионирования и правил жизненного цикла для отдельных версий файлов нет.
- Бакет Amazon S3 (выбрано). Хранилище не зависит от серверов и зон доступности, оплачивается
  только за объём и запросы. Браузер скачивает файл напрямую из S3. Минусы: нужно переписать
  модуль хранения и настроить роль и политику IAM.

## Последствия

- Пользователь получает файл так: приложение проверяет, что капсула открыта и пользователь
  может её видеть, затем отвечает кодом 302 с подписанным URL. Браузер скачивает файл из S3
  по HTTPS. Срок ссылки ограничен параметром `X-Amz-Expires=300` (5 минут), который входит
  в подпись. Изменить срок или ключ в ссылке нельзя без секретного ключа. Ссылка также перестаёт
  работать, когда истекают временные учётные данные роли, которыми она подписана.
- От случайного удаления файлы защищает версионирование: удаление создаёт маркер, а старые
  версии остаются. Политика приложения не разрешает `s3:DeleteObjectVersion`, поэтому приложение
  и тот, кто получит его учётные данные, не могут удалить версии навсегда.
- Рост стоимости ограничивает правило жизненного цикла `timecapsule-dev-noncurrent`: неактуальные
  версии через 30 дней переходят в Standard-IA, через 90 дней удаляются (кроме двух новых),
  незавершённые загрузки частями удаляются через 7 дней.
- Сервер приложения больше не хранит данные пользователей: на нём только код и настройки.
  Когда серверов станет несколько и перед ними появится балансировщик нагрузки, все серверы
  получат одну роль и будут работать с одним бакетом. Ничего синхронизировать не нужно,
  и любой запрос может обработать любой сервер. Elastic IP станет не нужен.
- Минус: приложение зависит от S3 и IAM. Ошибка в политике роли сразу ломает загрузку и скачивание.
  Локально код без роли не работает, проверять его нужно на сервере.
- Риск: бакет находится в одном регионе `eu-central-1`. При отказе региона вложения будут недоступны.
  Для защиты понадобится репликация в другой регион (Cross-Region Replication).
